LokuOn 段階6: VSTプラグイン対応の調査(11/9時点。調査のみで、実装はしていない)

0. 結論(先に)
 - 技術的・ライセンス的には可能。ただし「アプリ内でそのまま読み込む」方式は、録音アプリとしてはおすすめしない。
   プラグインが落ちるとLokuOn全体(=録音中のデータ)が道連れになるため。
 - おすすめ: 「VST専用の別プロセス(ヘルパーexe)」でプラグインを動かし、音は共有メモリでやり取りする。
   ヘルパーが落ちてもLokuOnは動き続け、そのエフェクトだけバイパスして録音を守れる。
 - ヘルパー側で NAudio.Vst3 を使えば、LokuOn本体は NAudio 2.2.1 のまま(大きな移行をしなくて済む)。
 - 実装は段階に分けて、最初は「1つのプラグインを1つの入力にかける試作」から。実機とプラグインでの確認が必須。

1. ライセンス(確認済み)
 - VST3 SDK は 3.8(2025年10月)から MIT ライセンス。署名・費用・登録は不要。以前の GPLv3/独自ライセンスの二択はなくなった。
 - 「VST」の商標・「VST Compatible」ロゴを使う場合だけ、Steinbergのガイドラインに従う(使わなければ不要)。
 - VST2(旧規格)のソースはこのライセンスの対象外で、新規に扱うのは法的にグレー。VST2だけのプラグイン(古いフリー品に多い)は対象外にするのが無難。
 - 個々のプラグイン自体のライセンス(再配布・商用利用)は、それぞれの作者のもの。LokuOnはプラグインを同梱しない。

2. .NET から使える選択肢
 A. NAudio.Vst3 3.3.0(MIT、作者 Mark Heath。2026年10月更新の安定版)
    - 探索・読み込み・処理・パラメータ/プリセット・エディタ画面まで対応。Windows専用、.NET 9。NAudio.Core 3.3.0以上が必要。
    - 課題: LokuOnは NAudio 2.2.1(Audioは net8.0)。NAudio 3 は .NET 9 以上が必須で、IWaveProvider/ISampleProvider が Span 方式に変わった
      (自作の RenderProvider などに影響)。WasapiOut/WasapiCapture は 3系にも当面残るが、次のメジャーで消える見込み。
      → 本体を移行せず「ヘルパーだけ NAudio 3」にすれば、この課題を避けられる。
    - 未確認: GitHub の README が読めなかったため、API の細部(エフェクトとして処理する呼び出し方、リアルタイム安全性、既知の不具合)は未確認。
 B. Vst3HostSharp 1.0.568(プレリリース、MIT、.NET 10、ダウンロード約1.5千)
    - C++の橋渡しDLLを同梱。実績が少なく、機能の範囲も資料から読み取れない。今回は候補から外す。
 C. 自前でVST3 SDKを使うネイティブのホスト(C++)
    - いちばん自由で確実だが、作る量が最も多い。A で問題が出たときの代替案。
 D. AudioPlugSharpHost
    - 自作プラグインを単体アプリにするためのもので、他社プラグインを読み込む用途ではない。対象外。
 参考: CLAP という別規格もあるが、対応プラグインがまだ少ない。まずVST3のみ。

3. 別プロセス方式(おすすめ)の設計案
 - 構成: LokuOn.exe ⇄ LokuOn.VstHost.exe(ヘルパー)。音は共有メモリ(MemoryMappedFile)のリングと、イベントで受け渡し。
 - 録音は元々 約0.3秒の遅延を持っているので、1ブロック(数ms〜10ms)の往復遅延は録音側では吸収できる。
   出力側(ヘッドホン等)は遅延に敏感なので、VSTは「録音側のエフェクト」から先に対応するのが現実的。
 - ヘルパーが落ちた/応答しない場合: その入力のVSTだけ即バイパスして音を通し続け、画面に通知。一定時間後に再起動を試す。
   同じ状況がNAudio.Vst3単体(アプリ内)だと、メモリアクセス違反は .NET で捕まえられず、アプリごと終了する。
 - プラグインの探索(スキャン)もヘルパーで行う。スキャン中に落ちるプラグインがあるため。
 - エディタ画面: ヘルパー側が独自のウィンドウで表示する(LokuOn本体の画面に埋め込まない)。DPIや描画の問題が本体に及ばない。
 - 設定の保存: プラグインの状態(getState)をバイト列として、プリセットに保存(Base64)。プラグインの場所(パス/ID)も保存し、見つからないときは警告。
 - かける位置の案: 入力ごとのFXの最後(リバーブの後)に「VST」を1〜2枠。出力ごとのFXにも同様に枠を追加できる。
 - サンプルレート・ブロックサイズ: エンジンは固定(48k想定)なので、プラグインにその設定を渡す。変更時は再初期化。
 - 配布: ヘルパーexeを同じ場所に同梱(GitHub Actions で一緒にビルド)。ファイルが増える/サイズが大きくなる点は要検討。

4. 注意点・リスク
 - x64のVST3のみ(32bit/VST2は対象外)。
 - プラグインごとに挙動がまちまち(遅延の報告、パラメータの扱い、起動の重さ)。実プラグインでの確認が必要。
 - CPU: 重いプラグイン(アンプシミュ、リバーブ等)は4入力すべてにかけると負荷が高くなる。プラグインごとの負荷表示があると安心。
 - 遅延補正: プラグインが報告する遅延(レイテンシ)を、他の入力とずれないように補正する必要がある。
 - 権利面: 有料プラグインのライセンス認証(オンライン認証など)が、ヘルパー経由で動くかはプラグイン次第。
 - 不確実: NAudio.Vst3 の品質・対応範囲(上記の通り README 未確認)。試作で最初に確かめる。

5. 段階案(実装する場合)
 6a 試作: ヘルパーexe + NAudio.Vst3 で、指定したVST3を1つ読み込み、共有メモリ経由で1入力にかける(画面は最小限)。音・遅延・CPUを実機で確認。
 6b プラグインの探索(スキャン)と選択画面、入力ごとの「VST枠」、プリセットへの保存(状態を含む)。
 6c エディタ画面の表示、パラメータの変更。
 6d 落ちたときのバイパスと再起動、遅延補正。
 6e (必要なら)出力側への対応。
 各段階の終わりに、ビルドして実機で確認する(これまでと同じ進め方)。

6. 決めてほしいこと
 - 使いたいプラグインがあれば名前を教えてほしい(VST3版があるか、別プロセスで動きそうかを先に調べられる)。
 - まず「録音側のエフェクト」に絞ってよいか(出力側は遅延の面で後回し)。
 - 6a の試作に進めてよいか。
